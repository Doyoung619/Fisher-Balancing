# Architecture and development

The three experiment engines are intentionally separate. They answer related but different questions; sharing an implementation name does not make their acquisition domains or reference targets interchangeable.

| Experiment | Configuration / queue | Estimation / acquisition | Execution / output |
|---|---|---|---|
| Continuous | `src/common.py` | `estimators.py`, `methods.py`, `oracles.py`, `reference.py` | `simulation.py`, `supervisor.py`, `checkpoint.py`, `metrics.py`, `plotting.py` |
| Sampled | `src/control.py` | `estimators.py`, `oracles.py`, `reference.py` | `simulation.py`, `control.py`, `diagnostics.py`, `plotting.py` |
| Real | `configs/*.yaml`, `common.py` | `numerics.py`, `selectors.py`, `family_selectors.py`, `evaluation.py` | `data.py`, `runner.py`, `runtime.py`, `aggregate_risk.py`, `reporting.py`, `artifacts.py` |

## Adding a method

For continuous acquisition, add the method ID/objective in `methods.py` and its numerical oracle in `oracles.py`, then explicitly revise the active method list/config validation in `common.py`. For sampled acquisition, register it in `control.py`, `oracles.py`, and plotting labels; decide whether acquisition is response-independent before reusing work. For real pools, implement it in `selectors.py` or `family_selectors.py`, register applicability, and add it to a copied YAML profile. `runner.py` already routes family-specific methods.

A useful algorithm test compares against a separately evaluated objective, checks feasibility and batch membership, and tests hidden-label independence. For a stateful algorithm, check interrupted/resumed output against an uninterrupted trajectory. Do not validate an algorithm solely by restating its implementation in a test.

## Protocol changes

Copy a real-response YAML into a new profile, change one scientific quantity at a time, and use a new output directory. `scripts/run_profile.py --config ...` accepts the retained batch, temperature, FB-opt/FB-opt2, and family-method presets without old campaign snapshots. The `fb_opt` and `fb_opt2` methods support Gaussian/Bernoulli only. B-EMCM/LCMD/RegVol support Gaussian; Entropy/FIRAL and BADGE support Bernoulli. Preserve these applicability limits when editing profiles.

Continuous YAML snapshots are generated by `python -m src.common --write-configs`. The execution path resolves the specification plus amendment in Python; editing only a YAML snapshot does not change `--prepare`. Deliberately update the resolver/specification for a new continuous protocol and document that change. Sampled presets are resolved by `make_config`; initialize a fresh run before changing its config.

## Scientific guardrails

The learner minimizes sum loss plus `rho/2 * ||theta||^2`. Synthetic fits constrain `||theta|| <= 4`. Real fits use penalized GLMs on nested, pool-fitted PCA features and include the intercept in the penalty. Temperature coefficients are fixed according to each protocol; resuming or extending a run must not recalibrate them from observed outcomes.

All selected responses arrive after a whole batch is chosen. Evaluation may use full-pool labels to fit references, but those references must remain inaccessible to selection. Full-history plug-in Fisher information must be reevaluated at the current terminal estimate for nonlinear families.

See [RESULTS.md](RESULTS.md) for aggregation order. Preserve signed errors, use the actual seed count, keep failures visible, and report uncertainty as descriptive Monte Carlo variation. A finite-seed directional eigenvalue estimate can be unstable, especially when the number of seeds is smaller than dimension.

## Useful next work

- Add independent acquisition certificates or better numerical error bounds for continuous Bernoulli oracles.
- Study sampled-cloud `K` sensitivity with saved states; retain the full-scan implementation as the numerical reference within each cloud.
- Add new GLM families only with objective/gradient/Hessian and leakage tests, then document what reference remains identifiable.
- Compare temperatures under fixed datasets, budgets, seed pairing, and feature transforms. Do not conflate `fb_sample`, `fb_range`, `fb_opt`, and `fb_opt2`.

The main development checks run in GitHub Actions on CPU. Data acquisition, historical result artifacts, and hardware-specific benchmarks are outside that job; no production-result claim follows from a green CI check.
